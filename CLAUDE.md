## What this system does

Automated crypto trading bot for Binance with three modes:
- **Backtest** — replay historical candles
- **Paper** — Binance testnet (no real money)
- **Live** — Binance mainnet (gated by explicit confirmation)

Signals come from rule-based strategies (RSI, EMA, MA crossover, volume) and/or an AI model. A risk engine sits between signal and execution; nothing reaches the order manager without passing risk checks.

## Architecture

```
[Frontend (React/Vite/TS)] ──HTTPS/WS──> [Backend (Go)] ──HTTP──> [AI Service (Python)]
                                              │
                                              └──REST/WS──> [Binance]
```

- **`apps/frontend`** — operator UI (dashboard, bot control, market watch, backtest, alerts)
- **`apps/backend`** (Go) — owns market data, strategy, risk, orders, paper/backtest, alerts, auth, API gateway. Stateful.
- **`apps/ai-service`** (Python) — datasets, features, training, model registry, inference. Stateless.

The Go backend is the **only** service that talks to Binance.

## Tech stack (do not deviate without discussion)

| Layer | Choice |
|---|---|
| Frontend | React 18 + Vite + TypeScript (strict) + MUI v5, `sx` prop **only** (no styled, no css prop, no Tailwind) |
| Frontend state | TanStack Query (server) + Zustand (client). **No Redux.** |
| Backend | Go 1.22+, `chi` router, `slog`, `context.Context` everywhere |
| AI service | Python 3.11+, FastAPI, uv, pydantic v2 |
| DB | PostgreSQL (trades, configs), Redis (market cache, pub/sub) |
| Transport | REST + WS Frontend↔Backend; HTTP/JSON Backend↔AI |

## Risk policy (enforce in code, not docs)

Every mode (backtest, paper, live). Violations must `error`, not `warn`.

1. **Position sizing** — no single position > `risk.max_position_pct` of equity (default 2%)
2. **Daily drawdown** — bot halts if realized + unrealized loss > `risk.max_daily_drawdown_pct` (default 5%)
3. **Stop loss required** — every order needs an associated stop loss; order manager rejects orders without one
4. **Slippage check** — market orders compute slippage from book depth; reject if > `risk.max_slippage_bps` (default 30)
5. **Live trading gate** — switching to live requires (a) explicit UI confirmation, (b) `LIVE_TRADING_ENABLED=true` env, (c) successful API key validation. Any missing → reject.
6. **Kill switch** — `POST /api/bot/kill` cancels all open orders, flattens, disables further entries

## Cross-service conventions

- **Time** — UTC, `int64` Unix milliseconds in transport. Local only at the UI edge.
- **Money** — never `float64`. Go: `decimal.Decimal` (shopspring). Python: `Decimal`. Transport as string ("0.00012345").
- **IDs** — ULID, lowercase, generated by the producer.
- **Logging** — structured. Required keys: `service`, `mode`, `symbol` (when applicable), `request_id`.
- **Errors** — never swallow. Return up the stack or log at `error` with full context.
- **Config** — YAML in `config/`, validated on startup. Env vars override file values. Never hardcode symbols, thresholds, API keys.

## What NOT to do

- Do not generate `plan.md`, `tasks.md`, `research.md`, `contracts/`, `quickstart.md`, or Spec-Kit-style scaffolding. Tests are the spec.
- Do not place real API keys, secrets, or `.env` content in any committed file
- Do not call Binance directly from the frontend or AI service
- Do not submit a market order without slippage check
- Do not enable live trading without all gate conditions
- Do not write CSS-in-JS via `styled` or `css` prop in frontend — `sx` only
- Do not use `float64`/`float` for money or price
- Do not add a third programming language. Use Go or Python for scripts.
